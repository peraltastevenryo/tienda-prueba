Ordena el viaje de un POST

Arrastra hasta dejarlo en el orden en que ocurre
⠿ ProductoRepository.save() y Hibernate escribe el INSERT
⠿ Spring responde 201 Created con el header Location y el producto en JSON
⠿ La app llama a fetch con POST, el header Content-Type y el body JSON
⠿ La app lee res.status y res.json() y muestra el producto nuevo
⠿ ProductoController recibe el JSON y @Valid revisa las reglas
⠿ Neon guarda la fila y entrega el id nuevo

Una respuesta HTTP tiene tres partes

201 Created
Location: /api/productos/7
Content-Type: application/json

{ "id": 7, "nombre": "Polerón", "descripcion": "Con capucha", "precio": 24990, … }
Código de estado
201 Created
Un número que resume cómo te fue. En la app se lee con res.status.
Headers
Location: /api/productos/7
Location dice dónde quedó el producto nuevo: lo pides con GET sin buscar su id.
Body
{ "id": 7, … }
El producto guardado, ya con su id. Se lee con res.json().
En un DELETE el código de estado es 204 No Content: llegan el código y los headers, pero el body viene vacío.

Las rutas nombran cosas, no acciones

El verbo ya lo pone el método HTTP. La ruta solo dice qué recurso es.

Así noAsí síRegla
✗ /api/getProductos✓ GET /api/productosSin verbos: el método ya dice la acción
✗ /api/borrarProducto?id=3✓ DELETE /api/productos/3Un recurso se identifica con {id} en la ruta
✗ /api/Producto✓ /api/productosSustantivo en plural y en minúsculas
✗ /api/buscarPorNombre/pol✓ GET /api/productos?nombre=polPara filtrar, un query param
✗ /productos✓ /api/productosPrefijo /api: separa los datos de lo demás
Jerarquía: lo que cuelga de algo va después. En otra tienda, /api/categorias/2/productos serían los productos de la categoría 2.

¿De quién es la culpa?

Mira el primer dígito

4xx: del cliente

La petición viene mal: un JSON inválido, un id que no existe, falta un header. Repetirla igual da el mismo error. Se arregla en la app.

o

5xx: del servidor

La petición estaba bien, pero el backend falló. El cliente no puede arreglarlo. Se arregla en el backend, y el detalle está en los Logs.

GET /api/productos/99 responde 404: pediste un id que no existe, culpa del cliente. Si Neon no contesta en medio de un GET /api/productos, responde 500: culpa del servidor.

Programamos juntos: las reglas de Producto

Anotaciones de Bean Validation

VS Code: Producto.java y ProductoController.java · luego Run sobre main y un POST sin nombre en Postman

@NotBlank(message = "El nombre es obligatorio")
@Size(max = 100, message = "El nombre puede tener como máximo 100 caracteres")
private String nombre;
@NotNull(message = "El precio es obligatorio")
@Min(value = 0, message = "El precio no puede ser negativo")
private Integer precio;
@PostMapping
public ResponseEntity<Producto> crear(@Valid @RequestBody Producto producto) {
@NotBlank rechaza un texto vacío o solo con espacios. @Size limita el largo. El message es lo que verá el usuario, así que va en español.
Un número no se valida con @NotBlank: lleva @NotNull para que no falte y @Min(0) para que no sea negativo. stock lleva las mismas dos.
Las anotaciones no hacen nada solas: @Valid en el parámetro le dice a Spring que las revise antes de entrar al método. Si algo falla, el método ni se ejecuta.

Programamos juntos: pedir datos con fetch

Archivo api.js, primera función

Expo: app-movil/src/api.js · se usa desde tu pantalla y se prueba con npx expo start y Expo Go

export const API_URL = 'https://tienda-render-ab12.onrender.com';
export async function listarProductos() {
  const res = await fetch(`${API_URL}/api/productos`);
  if (!res.ok) throw new Error(`Error ${res.status}`);
  return res.json();
}
La dirección base de tu API. Cambia tienda-render-ab12 por el nombre de tu servicio en Render. Sin barra al final, y nunca localhost.
fetch hace un GET si no le dices otra cosa. await espera la respuesta sin congelar la app, y por eso la función es async.
res.ok es true solo con códigos 2xx. fetch no falla solo por un 404 o un 500: lo revisas tú y lanzas el error con res.status.
res.json() lee el body y lo convierte en un arreglo de objetos JavaScript. También es asíncrono: devuelve una promesa.

Programamos juntos: crear con POST

Archivo api.js, segunda función

Expo: app-movil/src/api.js, debajo de listarProductos · se llama desde el botón Guardar

export async function crearProducto(producto) {
  const res = await fetch(`${API_URL}/api/productos`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(producto),
  });
  const data = await res.json();
  if (res.status === 400) throw { status: 400, campos: data.campos ?? {}, mensaje: data.mensaje };
  if (!res.ok) throw new Error(`Error ${res.status}`);
  return data; // 201
}
La función recibe el producto como objeto JavaScript y llama a la misma ruta que el listado: /api/productos.
Por defecto fetch hace GET. Para crear hay que decir POST.
Este header avisa que el body viene en JSON. Si lo olvidas, la API responde 415.
JSON.stringify convierte el objeto en texto JSON: el body siempre viaja como texto.
Se lee el body antes de revisar el código: en un 400 trae campos y mensaje. ?? {} cubre si no vienen.
Cualquier otro error (404, 500…) es un Error genérico. Si salió bien, data es el producto creado, ya con su id.

El celular no puede llamar a localhost

Dos formas de apuntar la app a tu API

✗ En tu PC

La app llama a http://localhost:8080. Para el celular, localhost es el propio celular, y ahí no corre ningún Spring Boot.

vs

✓ En internet

La app llama a una URL pública con HTTPS, como https://tienda-render-ab12.onrender.com. Responde desde cualquier celular y cualquier red.

Tu PC y tu celular son dos computadores distintos. Cada uno tiene su propio localhost, y el de tu celular está vacío.
